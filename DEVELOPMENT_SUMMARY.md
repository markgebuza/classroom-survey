## 3. Database configuration

The database is Supabase Postgres with five tables: `surveys`, `questions`, `choices`, `responses` and `answers`. Every table has a UUID primary key. Foreign keys connect them: a survey has many questions, a question has many choices, a survey has many responses, and a response has many answers (each answer points to a question and the chosen choice). Deleting a survey cascades to all of its data. CHECK constraints restrict `status` and `question_type`; a partial unique index (`only_one_active_survey`) allows only one active survey; a unique index on `(survey_id, anonymous_token)` blocks duplicate submissions; positions are unique per survey/question; a trigger maintains `updated_at`.

Row Level Security is enabled on all tables. The `anon` role (students) can only read active surveys and their questions and choices; all its other table privileges are revoked, so students can neither read results nor change anything. The `authenticated` role (the instructor) has full access, which is why public sign-ups are disabled. All writes by students go through `submit_survey_response`, a `SECURITY DEFINER` function that checks the survey is active, every question and choice belong together, every question is answered and the browser token has not been used, then inserts the response and its answers in one transaction and raises fixed error codes (`SURVEY_NOT_ACTIVE`, `DUPLICATE_RESPONSE`, …). Other RPC functions: `activate_survey` (closes the current active survey, generates an 8-character random slug, activates — in one transaction), `close_survey`, `get_survey_results` (counts and percentages in the API.md JSON shape), `duplicate_survey`, and `get_survey_status_by_slug` (so a student with an old QR code sees "closed" instead of "not found"). Every function has explicit `GRANT/REVOKE EXECUTE`.

## 4. How the frontend communicates with the database

The React app uses one `@supabase/supabase-js` client created from `VITE_SUPABASE_URL` and the public `VITE_SUPABASE_ANON_KEY`. There is no custom server: supabase-js calls Supabase's PostgREST API, which turns table queries into SQL, and calls RPC functions with `supabase.rpc(...)`.

- **Students** are never logged in, so their requests run as `anon`. The student page reads the active survey with a nested select (`surveys → questions → choices`) filtered by `public_slug`, and submits with `rpc('submit_survey_response')`. Errors are mapped to friendly messages in `src/lib/errors.ts`; raw database text is never shown.
- **The instructor** logs in with `signInWithPassword`. supabase-js then sends the user's JWT with every request, so Postgres sees the role `authenticated` and the full-access policies apply. The dashboard, editor, present page, results and CSV export use normal table queries (`select`, `insert`, `update`, `delete`, a count-only query for the live response counter) plus the RPC functions.

The security does not depend on the frontend: even with the anon key from the JavaScript bundle, `scripts/rls-probe.ts` shows that anon cannot read responses, change surveys or call the instructor functions.

## 5. Problems encountered and how they were resolved

All problems are listed in `AI_HISTORY.md` ("Problems & Fixes"). Three examples:

- **A test script that would have hidden its own results.** The first `rls_checks.sql` ended with `select …; rollback;`, but the Supabase SQL Editor only shows the last statement's output, so the results would never have been visible. The script now stores results in a temporary table, removes its own test data, commits, and selects the results as its final statement. Running it on PostgreSQL also caught a bug in the test data (a response without an answer), after which all 23 checks passed.
- **A build that looked fine but contained almost nothing.** The production bundle stayed the same size while pages were added. Without the Supabase environment variables, `src/lib/supabase.ts` throws at import time, and the bundler removed all the code after it. The build now prints a warning, and the README explains that the Cloudflare Pages variables must be set before the first build.
- **A security probe that reported false passes.** Pointed at an unreachable server, the first `rls-probe.ts` printed PASS for most checks, because "request failed" looked like "access denied". It now makes a preflight call that must succeed and only accepts Postgres "permission denied" or zero rows as a pass.

## 6. Deployment

The frontend is a static Vite build deployed on Cloudflare Pages from the GitHub repository: build command `npm run build`, output directory `dist`, environment variables `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` and `NODE_VERSION=22`. `VITE_PUBLIC_SITE_URL` is optional and not set: QR codes use the address the site is opened from, which in production is the Pages URL. `public/_redirects` sends every path to `index.html` so links like `/s/<slug>` work. The database schema comes only from the migration files, so it can be recreated in a new project.

- **Production URL:** https://classroom-survey-cky.pages.dev
- **GitHub repository:** https://github.com/markgebuza/classroom-survey
- **Deployed:** 2026-11-05. Every push to `main` redeploys automatically.
